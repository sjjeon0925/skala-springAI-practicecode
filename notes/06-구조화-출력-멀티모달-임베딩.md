## 쉽게 말하면 — 구조화 출력

*Day 2 · 구조화 출력*

- 답을 문장이 아니라 정해진 칸으로 받는다
- 받아서 자르고 파싱하는 코드가 사라진다
- 형식이 어긋나면 그 자리에서 실패하게 만든다

이렇게 생각하면 쉽다. 실제로는 이득.

| 자유 서술 답안지 | 문자열 응답 | 읽는 쪽에서 매번 해석해야 한다 |
| --- | --- | --- |
| 빈칸 채우기 양식 | record/클래스로 받기 | 코드가 바로 값을 쓴다 |
| 객관식 보기 제한 | enum으로 값 제한 | 없는 항목을 만들어 내지 못한다 |
| 양식 미준수는 반려 | 형식 위반 시 재요청 | 이상한 값이 흘러가지 않는다 |
| 표 여러 줄 | 목록 · 중첩 구조 | 복잡한 결과도 그대로 받는다 |

> **[지금은 이것만]** 문자열을 받아서 자르지 마라. 받을 모양을 미리 정해두고 그 모양으로 달라고 하면 된다 — 파싱 코드가 통째로 사라진다.

## 구조화 출력 — 텍스트를 객체로

*Day 2 · 구조화 출력*

- 응답을 문자열이 아니라 자바 객체로 받는다 — 파싱 코드가 사라진다
- Spring AI가 스키마를 프롬프트에 넣고, 결과를 변환해 준다

모델에 JSON 형식을 요청 → 응답 JSON을 Converter가 파싱 → record로 매핑.
`.entity(Person.class)` 한 줄이면 문자열 후처리가 사라진다.

```
JSON 형식 요청 → 모델 응답(JSON) → Converter 파싱 → record 매핑
```

`.entity(Person.class)` 한 줄이면 문자열 후처리가 사라진다.

## entity() — 한 줄로 객체 받기

*Day 2 · 구조화 출력*

- 결과 타입을 record로 정의하고 `.entity(타입)`으로 받는다
- List·Map 같은 컬렉션 타입도 지원

```java
record Review(String sentiment, int score,
    List<String> keywords) {}

Review r = chat.prompt()
    .user("다음 리뷰를 분석해줘:\n" + text)
    .call()
    .entity(Review.class);
// r.sentiment(), r.score(), r.keywords() — 타입 안전 (예시)
```

## JSON Schema — 모델이 보는 형식

*Day 2 · 구조화 출력*

- `entity()`가 붙이는 것은 사실 JSON Schema 문자열이다
- 필드 설명을 넣으면 정확도가 오른다 — 스키마도 프롬프트다
- `@JsonProperty` · `@JsonPropertyDescription`으로 스키마를 다듬는다

```java
record Ticket(
    @JsonPropertyDescription("BILLING·DELIVERY·REFUND·ETC 중 하나")
    String category,
    @JsonPropertyDescription("HIGH 는 결제·보안 문제일 때만")
    String priority,
    @JsonPropertyDescription("고객 문의를 한 문장으로 요약")
    String summary) { }

// 실제로 어떤 스키마가 붙는지 눈으로 확인해 보자
var converter = new BeanOutputConverter<>(Ticket.class);
System.out.println(converter.getFormat());
//  { "type":"object", "properties": {
//      "category": {"type":"string","description":"BILLING·DELIVERY..."} ...
//    }, "required":[...] }
```

## entity()는 안에서 무슨 일을 하나

*Day 2 · 구조화 출력*

- BeanOutputConverter가 타입 → JSON 스키마를 만들어 프롬프트에 덧붙인다
- 응답 문자열을 다시 JSON → 객체로 되돌린다 — 두 방향 모두 자동
- 직접 쓰면 형식 지시문을 내 프롬프트에 섞어 넣을 수 있다

```java
record Ticket(String category, String priority, List<String> tags) {}

var converter = new BeanOutputConverter<>(Ticket.class);
String template = "다음 문의를 분류하라.\n"
    + "{format}\n" // ← 스키마 지시문이 들어갈 자리
    + "문의: {inquiry}";

String answer = chat.prompt()
    .user(u -> u.text(template)
        .param("format", converter.getFormat()) // 자동 생성 스키마
        .param("inquiry", inquiry))
    .call().content();

Ticket ticket = converter.convert(answer); // 문자열 → 객체
```

## 목록으로 받기 — 여러 건을 한 번에

*Day 2 · 구조화 출력*

- 여러 건은 리스트 타입으로 — 제네릭은 ParameterizedTypeReference로 전달
- 구조가 유동적이면 `Map<String,Object>`도 가능하지만 타입 안전성을 잃는다
- 한 번에 N건을 받으면 호출 수가 줄어 비용·지연이 함께 준다

```java
record Keyword(String term, double score) {}

// ① 리스트로 받기 — 제네릭 타입 정보를 넘긴다
List<Keyword> keywords = chat.prompt()
    .user("다음 글의 핵심 키워드 5개를 점수와 함께: " + text)
    .call()
    .entity(new ParameterizedTypeReference<List<Keyword>>() {});

// ② 단순 문자열 목록
List<String> titles = chat.prompt().user("제목 후보 3개")
    .call().entity(new ListOutputConverter(new DefaultConversionService()));

// ③ 스키마를 못 정하겠을 때 (권장하지 않음 — 최후의 수단)
Map<String, Object> raw = chat.prompt().user(q)
    .call().entity(new MapOutputConverter());
```

## 타입 변환 함정 — enum·날짜·숫자

*Day 2 · 구조화 출력*

- 구조화 출력이 실패하는 곳은 대개 몇 가지 타입에 몰려 있다
- 모델은 "2026년 7월 30일"도 날짜라고 생각한다 — 형식을 지정해야 한다
- enum은 실패 대비 값을 하나 두는 편이 안전하다

| 타입 | 무엇이 문제인가 | 대응 |
| --- | --- | --- |
| enum | 목록에 없는 값을 만들어낸다 | UNKNOWN 같은 기본값을 목록에 포함 |
| LocalDate | "2026년 7월 30일" 등 자유 형식 | 설명에 yyyy-MM-dd 명시 |
| int/long | "약 3만원", "3,000" 처럼 문자 섞임 | "숫자만, 단위·쉼표 제외" 명시 |
| boolean | "네", "아마도"로 답한다 | 질문을 예/아니오로 명확히 |
| List | 빈 목록 대신 null을 준다 | "없으면 빈 배열" 명시 또는 null 처리 |
| 중첩 객체 | 깊어질수록 실패율이 오른다 | 2단계까지 · 넘으면 호출을 쪼갠다 |

> **[주의]** enum에 UNKNOWN을 넣어두라. 없으면 모델이 억지로 아무 값이나 고르고, 그 잘못된 분류가 조용히 흘러간다 — 오류보다 나쁘다.

## 구조화 출력이 깨졌을 때 — 복구 전략

*Day 2 · 구조화 출력*

- 모델은 가끔 설명을 덧붙이거나 코드펜스로 감싸 JSON 파싱을 깨뜨린다
- 1차 정제(펜스 제거) → 2차 재요청(형식만 다시) → 3차 기본값
- 재요청은 원문을 함께 주면 성공률이 크게 오른다

```java
public Ticket classify(String inquiry) {
    try {
        return chat.prompt().user(inquiry).call().entity(Ticket.class);
    } catch (Exception first) { // 형식 위반
        try { // 형식만 다시 요청
            return chat.prompt()
                .system("반드시 JSON 객체만 출력한다. 설명·코드펜스 금지.")
                .user("아래를 스키마에 맞게 다시 정리하라:\n" + inquiry)
                .options(ChatOptions.builder().temperature(0.0).build())
                .call().entity(Ticket.class);
        } catch (Exception second) { // 그래도 실패
            log.error("재요청도 실패 — 기본값 반환", second);
            return new Ticket("UNKNOWN", "NORMAL", List.of());
        }
    }
}
```

> **[주의]** 구조화 출력은 거의 성공한다 — 그 "거의"가 운영에서 장애가 된다. 온도 0 + 재요청 1회 + 안전한 기본값, 이 세 겹이면 대부분 막힌다.

## 긴 문서 처리 — 나누고 합치기

*Day 2 · 멀티모달과 임베딩*

- 컨텍스트 창을 넘는 문서는 한 번에 넣을 수 없다
- Map-Reduce(나눠 요약 후 합치기) 또는 Refine(누적 갱신) 두 방식
- Map-Reduce는 빠르고 병렬, Refine은 맥락 유지가 낫다

```java
// ① Map — 조각별로 요약 (병렬 가능)
List<String> partials = chunks.parallelStream()
    .map(c -> chat.prompt().user("핵심만 5문장 요약:\n" + c).call().content())
    .toList();

// ② Reduce — 요약들을 다시 하나로
String summary = chat.prompt()
    .system("여러 조각 요약을 하나의 일관된 글로 합친다. 중복은 제거한다.")
    .user(String.join("\n---\n", partials))
    .call().content();

// ── 대안: Refine — 앞 결과를 이어받아 갱신 (순차, 맥락 유지에 유리)
String running = "";
for (String c : chunks) {
    running = chat.prompt()
        .user("기존 요약:\n" + running + "\n\n새 내용을 반영해 갱신:\n" + c)
        .call().content();
}
```

## 그 밖의 모달리티 — 이미지 생성·음성

*Day 2 · 멀티모달과 임베딩*

- Spring AI는 텍스트 외에 이미지 생성·TTS·STT도 같은 방식으로 추상화한다
- 인터페이스만 다를 뿐 주입받아 호출하는 형태는 동일하다
- 비용 단위가 다르다 — 이미지는 장당, 음성은 초당

| 기능 | 인터페이스 | 비용 단위 | 실무 용도 |
| --- | --- | --- | --- |
| 텍스트 생성 | ChatModel | 토큰 | 대화 · 분류 · 요약 |
| 임베딩 | EmbeddingModel | 입력 토큰 | 검색 · RAG |
| 이미지 생성 | ImageModel | 장당 | 썸네일 · 시안 |
| 음성 합성(TTS) | TextToSpeechModel | 문자 수 | 안내 음성 · 접근성 |
| 음성 인식(STT) | Transcription…Model | 오디오 길이 | 상담 녹취 → 텍스트 |

```java
@Service
class VoiceService {
    private final TextToSpeechModel tts; // 주입 방식은 ChatModel 과 같다

    public byte[] speak(String text) {
        return tts.call(new TextToSpeechPrompt(text)).getResult().getOutput();
    }
}
```

- ch05.structured를 참고한다

| 단계 | 무엇을 한다 | 확인 기준 |
| --- | --- | --- |
| ① | 문의 분류 결과를 문자열로 받아 직접 파싱 | 형식이 조금만 달라도 깨진다 |
| ② | record 정의 후 `.entity(Class)`로 교체 | 파싱 코드가 통째로 사라진다 |
| ③ | 카테고리를 enum으로 바꾸기 | 허용값 밖이 오면 실패한다 |
| ④ | 목록·중첩 구조로 확장 | `List<Item>`도 그대로 매핑된다 |
| ⑤ | 모델이 형식을 어기게 유도한 뒤 복구 처리 | 재요청 또는 기본값 — 화면은 살린다 |
| ⑥ | 이미지 한 장으로 멀티모달 호출 (선택) | 같은 ChatClient로 처리된다 |

> **[주의]** ⑤번을 건너뛰지 마라. 구조화 출력은 대부분 잘 되지만, 100번 중 한 번 어긋난다 — 그 한 번을 어떻게 처리할지 정해두는 것이 실서비스다.

## 실습 코드 — 영화 감상문 → 별점 카드

*Day 2 · 멀티모달과 임베딩*

- 문자열이 아니라 카드(객체)로 받는다
- 보기를 enum으로 제한해 헛소리를 막는다
- 파싱 코드가 통째로 사라진다

```java
enum 느낌 { 최고, 좋음, 보통, 별로 } // ① 보기를 제한한다

record 리뷰카드(String 제목,          // ② 받을 모양을 미리 정한다
    느낌 감정,
    int 별점,                       // 1~5
    List<String> 키워드) {}

@RestController
class ReviewLab {
    private final ChatClient chat;

    ReviewLab(ChatClient.Builder b) { this.chat = b.build(); }

    @GetMapping("/lab6/review")
    리뷰카드 card(@RequestParam String text) {
        return chat.prompt()
            .system("영화 감상문을 카드로 정리한다. 별점은 1~5 정수로 매긴다.")
            .user(text)
            .call()
            .entity(리뷰카드.class); // ③ 객체로 받는다 (파싱 없음)
    }
}

// ?text=연출은 좋은데 결말이 아쉬웠다
// { "제목":"아쉬운 결말", "감정":"보통", "별점":3,
//   "키워드":["연출 좋음","결말 아쉬움"] }
// ④ 모델이 '느낌' 에 없는 값을 만들면? → 그 자리에서 실패한다. 그게 안전하다.
```

## 실행·테스트 — 별점 카드

*Day 2 · 멀티모달과 임베딩*

- 리뷰 두 개로 호출해 별점이 정수로 오는지 본다
- 문자열이 아니라 객체로 온다 — 이 실습은 그게 전부다
- 테스트는 별점이 1~5 안에 있는지만 보면 충분하다

```
# 1) 파일 위치
src/main/java/com/skala/lab6/ReviewLab.java
#    → 실행: SpringAI_실습/06_별점카드 폴더를 VS Code 로 열고 F5 (또는 ./gradlew bootRun)

# 2) 호출
curl 'localhost:8080/lab6/review?text=연출은 좋은데 결말이 아쉬웠다'
curl 'localhost:8080/lab6/review?text=인생 영화. 세 번 봤다'

# 3) 기대 결과 — 문자열이 아니라 JSON 객체
{"제목":"아쉬운 결말","감정":"보통","별점":3,"키워드":["연출 좋음","결말 아쉬움"]}

# 4) enum 실험 — 보기 밖의 값을 유도해 본다
curl 'localhost:8080/lab6/review?text=뭐라 말하기 애매한 영화'
#   '애매함' 같은 새 값이 오면 → 변환 단계에서 실패한다 (그게 안전하다)

# 5) 테스트 — 타입과 범위를 검증한다
@Test void 카드_형식이_지켜진다() {
    리뷰카드 c = lab.card("연출은 좋은데 결말이 아쉬웠다");
    assertThat(c.감정()).isNotNull();       // enum 이라 값이 보장된다
    assertThat(c.별점()).isBetween(1, 5);
    assertThat(c.키워드()).isNotEmpty();
}

# 안 되면 — 변환 실패: 필드 이름이 프롬프트 설명과 어긋남
#           별점이 0 이나 6: 프롬프트에 범위를 명시한다
```

## 핵심 요약 — 구조화 출력과 멀티모달

*Day 2 · 멀티모달과 임베딩*

- 이 장의 결론 — 문자열을 파싱하지 말고 객체로 받는다
- 여기서부터 AI 응답을 서비스 코드에 안전하게 붙일 수 있다

| 개념 | 한 줄 정리 | 실무 포인트 |
| --- | --- | --- |
| entity() | 타입만 주면 객체로 받는다 | record로 못 박아라 — Map은 최후의 수단 |
| BeanOutputConverter | 타입 → 스키마 → 프롬프트에 첨부 | 형식 지시문 위치를 정할 때 직접 쓴다 |
| 목록·중첩 | ParameterizedTypeReference 사용 | 한 번에 N건 — 호출·비용 절감 |
| 실패 복구 | 온도 0 → 형식 재요청 → 기본값 | "거의" 성공이 운영에선 장애다 |
| 멀티모달 | 이미지 + 텍스트를 함께 | 토큰을 많이 쓴다 — 해상도부터 줄인다 |
| 임베딩·토큰 | 검색의 재료이자 비용의 단위 | 긴 문맥은 요약 후 투입 |

> **[체크]** 구조화 출력 코드에 try-catch가 없다면 천 건 중 몇 건이 그대로 장애 알람이 된다.
